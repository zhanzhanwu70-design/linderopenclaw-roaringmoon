### 3. 架構發現一：Agent Loop 是「同質可注入的 trait 對」

#### 兩個關鍵 trait（conversation.rs:38-44）

```rust
pub trait ApiClient {
    fn stream(&mut self, request: ApiRequest) -> Result<Vec<AssistantEvent>, RuntimeError>;
}

pub trait ToolExecutor {
    fn execute(&mut self, tool_name: &str, input: &str) -> Result<String, ToolError>;
}
```

兩個 trait **都只用 `&mut self`** — 不允許並行，但允許可變狀態（計數器、連線池、cache）。

`ConversationRuntime<C, T>` 是泛型 struct，編譯期強制把兩個具體 impl 釘死。

#### 三層實作組合（main.rs:2833）

```rust
ConversationRuntime::new_with_plugins(
    session,                                              // Session
    AnthropicRuntimeClient::new(...),                     // C = ApiClient
    CliToolExecutor::new(allowed_tools, emit_output, ...), // T = ToolExecutor
    permission_policy(mode, ...),                         // PermissionPolicy
    system_prompt,
    feature_config,
    plugin_registry,                                      // PluginRegistry
)
```

DI 在 main.rs 一個函式裡完成，runtime 本身不知道 Anthropic、不知道 CLI renderer、不知道 plugin。

#### run_turn() — 整個 agent loop（conversation.rs:317-472, 156 行）

```
loop {
  iterations += 1;                                          // 1. 計算迭代
  if iterations > self.max_iterations {                     //    無限循環防護
    return Err(...);
  }
  let request = ApiRequest {                                // 2. 組裝 prompt
    system_prompt: self.system_prompt.clone(),
    messages: self.session.messages.clone(),                //    整個 session 歷史
  };
  let events = self.api_client.stream(request)?;            // 3. 呼叫 LLM
  let (assistant_message, usage) = build_assistant_message(events)?;
  self.usage_tracker.record(usage);                         //    累計 token
  
  // 把 assistant 訊息推進 session
  self.session.messages.push(assistant_message.clone());
  
  // 抽出所有 tool_use blocks
  let pending_tool_uses = assistant_message.blocks
    .iter().filter_map(...).collect();
  
  if pending_tool_uses.is_empty() { break; }                // 4. 沒 tool call 就結束
  
  for (tool_use_id, tool_name, input) in pending_tool_uses {
    // 5. PreToolUse hooks (built-in + plugin)
    // 6. 權限檢查
    // 7. 執行 tool
    // 8. PostToolUse hooks
    // 9. 把 tool_result 推進 session.messages
  }
}
```

**最大觀察**：
- **整個 session 每次都重傳**：`messages: self.session.messages.clone()` — O(n²) 成本
- 沒有「partial update」、「append-only」、「diff」最佳化
- `compact.rs` 23396 bytes 顯然是為了解決 O(n²) — 對話太長就壓縮

#### hook 流程：雙層 hook（built-in + plugin）

每一個 tool call 跑 4 個 hook：
1. `run_pre_tool_use_hook` — `HookRunner` (built-in)
2. `run_plugin_pre_tool_use` — `PluginHookRunner` (外掛)
3. 執行 tool
4. `run_post_tool_use_hook` / `run_post_tool_use_failure_hook` — built-in
5. `run_plugin_post_tool_use` — plugin

Hook 可以做的事：
- `updated_input()` — **改寫 tool 的輸入**（最 powerful）
- `permission_override()` — 強制 Allow/Deny
- `messages()` — 附加 system-style 訊息到 tool result
- `is_denied()` / `is_cancelled()` — 攔截

**這個 hook 設計是 Claude Code agent 安全的核心** — LLM 看起來呼叫了 `Bash("rm -rf /")`，但 hook 可以在執行前改寫成 `Bash("echo 'denied'")` 或插入「Hook feedback: This is destructive」到 tool result。

### 4. 架構發現二：`GlobalToolRegistry` 是 builtin ⊕ plugin 的集合體

#### 結構（tools/src/lib.rs:74-228）

```rust
enum RegisteredToolHandler {
    Builtin,
    Plugin(PluginTool),
}

struct GlobalToolRegistry {
    entries: Vec<RegisteredTool>,
}
```

`with_plugin_tools(plugin_tools)`：
1. 從 `Self::builtin()` 開始（用 `mvp_tool_specs()` 拉所有內建）
2. 每個 plugin tool 用 `normalize_registry_tool_name` 去比對
3. 已存在同名 → **fail-fast 錯誤**（"plugin tool X from Y conflicts with Z"）
4. 不存在 → 推進 `entries`，handler = `Plugin(tool)`

#### dispatch（tools/src/lib.rs:221-227）

```rust
pub fn execute(&self, name: &str, input: &Value) -> Result<String, String> {
    let entry = self.find_entry(name)
        .ok_or_else(|| format!("unsupported tool: {name}"))?;
    match &entry.handler {
        RegisteredToolHandler::Builtin => execute_tool(&entry.definition.name, input),
        RegisteredToolHandler::Plugin(tool) => tool.execute(input).map_err(...),
    }
}
```

名字 → `RegisteredTool` 線性掃描（不是 HashMap）。entries 數量約 30 個（內建） + N 個 plugin，所以線性 O(n) 沒問題。

#### CliToolExecutor 是 thin 包裝（main.rs:3680-3735）

```rust
impl ToolExecutor for CliToolExecutor {
    fn execute(&mut self, tool_name: &str, input: &str) -> Result<String, ToolError> {
        // 1. allowed_tools 過濾
        // 2. 解析 input 為 serde_json::Value
        // 3. tool_registry.execute(tool_name, &value)
        // 4. emit_output 時順便 stream 到 stdout
    }
}
```

兩個責任：
- **policy**（--allowedTools 過濾）
- **presentation**（emit 給終端機看的 markdown）

實際 dispatch 邏輯全在 `GlobalToolRegistry`。

### 5. 架構發現三：Session 是「JSON file on disk」

#### ContentBlock 種類（session.rs:18-32）

```rust
pub enum ContentBlock {
    Text { text: String },
    ToolUse { id, name, input: String },
    ToolResult { tool_use_id, tool_name, output: String, is_error: bool },
}
```

只有三種。**沒有 Image、沒有 Audio、沒有 thinking、沒有 tool_use_delta（streaming 增量）**。

→ 整個 session 是「一次寫一塊」的 chunky 模式，stream event 只在 API 層，落地時就聚合了。

#### 持久化

`save_to_path` / `load_from_path` 是「整個 session 一次寫到一個 JSON 檔」 — **不是 JSONL**。昨天報告（`query_engine.py` 的 `transcript_store`）講的 JSONL 是 Python port 的格式，跟 Rust core 對不上。

這可能是 Python port 自己發明的格式（為了 stream-friendly 寫入），Rust core 沒走那條路。

#### API 契約（ApiRequest）

```rust
pub struct ApiRequest {
    pub system_prompt: Vec<String>,
    pub messages: Vec<ConversationMessage>,
}
```

`system_prompt` 是 **`Vec<String>`**，不是單一字串 — 表示可以分段組合（base prompt + project context + tool reminders），實作上靠 `SystemPromptBuilder` 組。

### 6. 全鏈路追蹤：一個 prompt 的旅程

```
[CLI: readline input]
    ↓ rusty-claude-cli
[AnthropicRuntimeClient::stream]
    ↓
[Anthropic API, SSE events]
    ↓
[Vec<AssistantEvent> — TextDelta/ToolUse/Usage/MessageStop]
    ↓
[ConversationRuntime::run_turn]
    ├─ build_assistant_message → ContentBlock::Text + ToolUse
    ├─ for each ToolUse:
    │   ├─ PreToolUse hooks (built-in + plugin)
    │   ├─ permission_policy.authorize_with_context
    │   ├─ CliToolExecutor::execute
    │   │   ├─ allowed_tools filter
    │   │   ├─ JSON parse
    │   │   └─ GlobalToolRegistry::execute
    │   │       ├─ Builtin → execute_tool() → e.g. file_ops::read_file
    │   │       └─ Plugin → PluginTool::execute → Command::spawn() → JSON over stdin/stdout
    │   ├─ PostToolUse hooks
    │   └─ ContentBlock::ToolResult push 到 session.messages
    └─ loop until no pending_tool_uses
[Session::save_to_path]  ← 一次 JSON 寫到磁碟
```

**訊息流的單向性**：session.messages 是 single source of truth，agent loop 一直在 mutate 這個 vec。
**權限的層次化**：(1) hook override → (2) permission_policy + prompter → (3) tool handler

### 7. 對未來在我們系統使用的影響

1. **trait 對（ApiClient + ToolExecutor）是好模板**
   - 我們要接 Claude / OpenAI / 本地 LLM，只要寫一個 `ApiClient`
   - 我們要支援 plugin / function calling，只要寫一個 `ToolExecutor`
   - Runtime 完全不用改
   - **可直接搬**（整個 conversation.rs 加上 session.rs 約 1700 行）

2. **O(n²) session 設計是致命傷**
   - 每次 API call 重傳整個 messages vec
   - 對長對話（>50 輪）就會卡
   - 必須自己加：partial delta API、append-only message store、或 Anthropic prompt cache
   - **auto-compaction 200k 是必要緩衝**，但 prompt cache miss 時 token 帳單會爆

3. **Hook 系統值得完整抄**
   - Pre/Post + 4 個粒度（built-in / plugin / success / failure）已經覆蓋大部分需求
   - `updated_input()` 是 killer feature — LLM 看不到 hook 改寫
   - 缺：沒有 streaming hook（hook 結束前 model 看不到任何 output）

4. **缺 streaming-aware session**
   - ContentBlock 沒有 incremental 型別
   - 想加 streaming 顯示得動 ContentBlock enum + 所有 consumer
   - 估計這是 claw-code vs upstream Claude Code 的差異（後者有 streaming-friendly session）

5. **StaticToolExecutor 模式很實用**
   - `BTreeMap<String, Box<dyn FnMut>>` — 測試時直接 `register("add", |input| Ok("4"))`
   - 不用 mock framework 就能 unit test
   - 抄到我們的 runtime 也不錯

6. **`GlobalToolRegistry` 的 fail-fast 衝突偵測**
   - 比 runtime 攔截好太多
   - **採用**：啟動時 name collision 就 return Err
