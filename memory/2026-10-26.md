### 真正嚴重的問題（比 429 嚴重）
`/home/amr/llm-wiki` 的 git **真實 index 落後 HEAD**：nightly sync `push-llm-wiki.sh` 用 isolated index（`GIT_INDEX_FILE`）+ `update-ref` 造 commit，只動 ref 不更新真實 `.git/index`。

後果：19 個**仍在磁碟上、也仍在 HEAD 裡**的 wiki 頁面被 git 標成「staged deletion + untracked」。
- `git commit --dry-run` 實測 **426 筆刪除**
- 受害頁面含 `wiki/people/李厚辰.md`、`wiki/topics/台灣民主.md`、9 個 concepts、4 個 sources
- **觸發條件：任何「不先 `git add -A`、直接 `git commit`」的操作**。`backup-openclaw.sh` 反而安全（`git add -A` 會把 index 同步回 working tree）

### 修復
```bash
# 只動 index、不動 working tree
git diff --cached --name-only --diff-filter=D -z -- wiki/ \
  | git restore --staged --pathspec-from-file=- --pathspec-file-nul
git reset          # index → HEAD，working tree 不動
```
驗證：`comm` 差集 = 0、staged deletion = 0、index vs HEAD drift = 0。

### 機制修正（09:0x 實測確認，後來在隔離 clone 重驗）
前一版的描述不夠精確。真正的觸發條件是「**誰先 commit**」，不是「isolated index 本身有害」：

> agent 把檔案寫到磁碟但**未自行 `git add`／`git commit`** → nightly sync 用 isolated index 把這些路徑 commit 進 HEAD → **真實 index 從未見過它們** → 之後任何人（或 weekly research cron）跑 `git add <自己的檔案> && git commit` → 那批路徑**從 HEAD 被刪除**（檔案仍在磁碟上，status 同時出現 `D` + `??`）

- **對照組:** agent 若在 nightly 前自己先 commit → drift=0 → 安全
- **數量對帳:** 05:05 的 `4ac2858630` 正好新增 **19 個檔案**，就是被標成 `D` 的那 19 個 —— 吻合
- **修法實測:** `git reset -q HEAD` 後 drift=0，後續 `git add X && git commit` 不再誤刪；未提交檔案仍正確顯示 `??`（reset 不吃 working tree）
