### 根因：**arXiv API 的 HTTP 429，不是查詢語法錯誤**
- 我用同樣的 `%22` 編碼重跑那兩個查詢 → **現在完全正常**（`livelock` 回 5 筆、`termination AND LLM` 回 56 筆）→ 語法與編碼都沒錯
- 實測快速連打：前 12 發正常，**第 13 發起 arXiv 改回 `HTTP/2 429` 且 body 為空**
- 空 body 餵給 `xml.etree.ElementTree` → 就會印成 **`ERR mismatched tag` / `ERR syntax error`**，而不是乾淨的 429 → **錯誤訊息把「被限流」誤裝成「查詢寫錯」**
- **教訓：arXiv API 的限流不是 429 文字回應，而是 429 + 空 body。** 解析前要先看 HTTP code / body 長度，別讓 XML parser 的錯誤訊息誤導方向
- **可重用修法**：查詢之間 `sleep 3`（arXiv 官方建議的節流）；或改用 `arxiv.org/html/<id>` 直取（不受 API 限流影響）

## 09:35 排程健康巡檢：早上的失敗分成「三種病因」，別混為一談
<!-- project: github.com/zhanzhanwu70-design/linderopenclaw-roaringmoon -->
把 08:10 之後所有失敗的 cron 逐筆拉出來看（`openclaw cron runs --id <job>`），發現三種**不同**的病因：
- **HTTP 429 overloaded（研究型 isolated cron）**：`群體智能架構研究`（error 5x）診斷寫得很清楚 —— `HTTP 429: {"type":"error","error":{"type":"overloaded_error","message":"server is busy, please retry later"}}`，來源標記 `agent-run`。**是 MiniMax 後端過載，不是 query/任務邏輯錯。**
- **cron 600s timeout（heartbeat 類）**：`heartbeat:rowlet` 09:18 / 09:29、`heartbeat:gengar` 09:10 / 09:21 / 09:32、`heartbeat:roaringmoon` 08:56 都是 `cron: job execution timed out`，durationMs ≈ 600000 → **模型呼叫掛住**（與 429 同一時段，provider 端不穩）。
- **設定層問題（與 provider 無關）**：`heartbeat skipped: no-route`（gengar 08:30，259ms 就結束）與 `heartbeat failed: Discord bot token missing for account "default"`（rowlet 08:39，61s）。`openclaw status` 也明講 `waiting for delivery route — set commands.ownerAllowFrom or channel allowFrom, or heartbeat.target`。

### 關鍵結構性發現：fallback 擋不住這次過載
<!-- project: github.com/zhanzhanwu70-design/linderopenclaw-roaringmoon -->
`agents.defaults.model = {primary: minimax-portal/MiniMax-M3, fallbacks: [minimax/MiniMax-M3]}` —— **primary 與 fallback 都是 MiniMax 家族**，MiniMax 後端一忙，兩者一起掛。`agents.defaults.modelPolicy.allow` 裡有 `openai/gpt-5.4-mini` / `gpt-5.4-nano` 可用。**若要讓 over-load 時刻的研究 cron 有機會完成，fallback 清單需要跨 provider（例如加 openai/gpt-5.4-mini）。**（改全域 model 設定 = 影響全部 agent 的 config 變更，先回報 Linder 再動。）
