## 🔗 Hook System 核心設計

ClawCode 的 hooks 是發生在 tool 執行前後的外部命令 pipeline，是系統的安全/擴充性邊界。

### 三種 Hook Events
```
PreToolUse        — tool 執行前
PostToolUse       — tool 成功後
PostToolUseFailure — tool 錯誤後
```

### 執行流程

`HookRunner::run_commands()` 對每個配置的 command 逐一：
1. 以 shell  spawn 子行程
2. 注入環境變數：`HOOK_EVENT`、`HOOK_TOOL_NAME`、`HOOK_TOOL_INPUT`、`HOOK_TOOL_IS_ERROR`、`HOOK_TOOL_OUTPUT`
3. 將 JSON payload 送至 stdin：
   ```json
   {
     "hook_event_name": "PreToolUse",
     "tool_name": "read",
     "tool_input": <parsed object>,
     "tool_input_json": "<raw JSON>",
     "tool_output": null,
     "tool_result_is_error": false
   }
   ```

### Hook 回應合約

Command 透過 stdout 回傳 JSON 控制行為：
```json
{
  "systemMessage": "可選訊息",
  "reason": "可選原因",
  "continue": false,              // 或 "decision": "block" → deny
  "hookSpecificOutput": {
    "permissionDecision": "allow|deny|ask",   // 覆寫權限決策
    "permissionDecisionReason": "原因文字",
    "updatedInput": <任何 JSON>              // 可修改 tool 輸入
  }
}
```

Exit code：`0`=允許、`2`=拒絕、其他=警告

### Abort 機制
`HookAbortSignal`（atomic bool）可在執行前/中取消。CLI 的 `HookAbortMonitor` 會將 Ctrl+C 轉換為 hook abort。

## 🔐 Permission System 分層設計

```
ReadOnly < WorkspaceWrite < DangerFullAccess
Prompt (特殊：永遠問)
Allow (繞過所有檢查)
```

**授權流程**（`authorize_with_context`）：
1. 若 `deny_rules` 匹配 → 直接拒絕
2. 若 `context.override_decision` 有值（來自 hook）→ 優先採用
3. 若 `ask_rules` 匹配 → 彈 prompt
4. 若 `allow_rules` 匹配 或 `active_mode >= required_mode` → 允許
5. 否則 → 拒絕

**Rule 語法**：
```
toolname              → 匹配該 tool 所有輸入
toolname(*:* )       → wildcard
toolname(path:/foo/*) → 前綴匹配（從 JSON 抽取路徑比對）
```

#### 1️⃣ Sandbox 沙盒隔離 (`sandbox.rs`)

**核心概念：** ClawCode 實現了三層隔離機制，使用 Linux namespace + mount + `unshare` 達成。

| 模式 | 說明 |
|------|------|
| `Off` | 不隔離 |
| `WorkspaceOnly` | 只能寫入工作區 |
| `AllowList` | 只允許寫入白名單目錄 |

**容器偵測策略（很聰明）：**
- 檢查 `/.dockerenv`、 `/run/.containerenv` 
- 讀取 `/proc/1/cgroup` 找 docker/containerd/kubepods/libpod 等關鍵字
- 掃描環境變數：`container`、`docker`、`podman`、`kubernetes_service_host`

**Sandbox 請求鏈：**
```
SandboxConfig → resolve_request() → SandboxRequest 
                                    ↓
                         resolve_sandbox_status_for_request()
                                    ↓
                          build_linux_sandbox_command()
                                    ↓
                              使用 unshare 執行
```

**重要細節：** 當 namespace 或 network 隔離 requested 但 `unshare` 不可用時，會進入 **fallback 模式**，記錄原因但不會整個 fail——這是graceful degradation 設計。

**對我們的影響：** 若想在 OpenClaw 實現隔離 exec，可以參考這套偵測 + 降級機制，避免在不支持的環境下crash。

#### 2️⃣ Permissions 權限系統 (`permissions.rs`)

**權限模式層級（從低到高）：**
```
ReadOnly < WorkspaceWrite < DangerFullAccess < Prompt < Allow
```

**核心邏輯：`authorize_with_context()`**

決策順序（重要）：
1. **Deny 規則優先** — deny 規則搶劫一切
2. Hook override → **Deny**（直接阻擋）
3. Hook override → **Ask**（強制 prompt）
4. Hook override → **Allow** → 但若遇到 ask rule，仍需 prompt
5. **Ask 規則** → 觸發 prompt
6. **Allow 規則** → 直接放行
7. 當前 mode ≥ required mode → 放行
8. Prompt mode → prompt
9. 預設 → Deny

**規則匹配語法（有趣的 DSL）：**
```
bash(git:*)      → tool=bash, prefix="git:"
bash(rm -rf:*)   → tool=bash, exact="rm -rf"
bash             → tool=bash, any
```

支援 escape：`\(` 和 `\)` 允許在 tool name 或 pattern 中包含括號。

**對我們的影響：** 這套 `PermissionRule` + `PermissionPolicy` 架構很值得借鑒。若 OpenClaw 要實現 tool-level 權限控制，可以直接套用這個決策樹，只是把 `unshare` 改成我們的沙盒 API。

## Hardware vs Software Collision — 根本差異

### Hardware Collision Control

**服務**：`io_module/set_parameters`（直接硬體 IO 控制）

```cpp

rclcpp::Parameter("open_collision", true)  // true = 開啟, false = 關閉
```

**本質**：直接控制實體機器人的 **安全電路 IO**。

當你對 IO module 說 `open_collision: true`，等於是告訴硬體「可以把碰撞偵測打開了」——這是電路層面的開關，不是軟體邏輯。是一個**binary 的硬體訊號**。

### Software Collision Monitor

**服務**：`amr_collision_monitor_server/command`

```cpp
// 發送的命令有三種：
STOP, START, STOP_ALL
// 帶 monitor_name 和 update 參數
```

**本質**：獨立的 `nav2_collision_monitor` ROS 節點，用 **LiDAR / Depth Camera** 的感測器資料，实时計算多層級的虛擬圍欄（polygons）。

軟體監控可以設定：
- `PolygonStop`：進入就停車
- `PolygonWarning1`：進入就減速 30%
- `PolygonWarning2`：進入就減速 50%
- `FootprintApproach`：根據行駛方向動態擴展偵測範圍

## 為什麼要分開？

| 維度 | Hardware Collision | Software Collision |
|---|---|---|
| **觸發來源** | 實體 IO 腳踏墊/紅外線感測器 | LiDAR / Camera 軟體計算 |
| **回應速度** | 硬體即時（微秒級）| 軟體延遲（數十毫秒）|
| **邏輯** | Binary（開/關）| 多層級（stop / slowdown / approach）|
| **失敗模式** | IO 硬體故障時仍有物理保護 | 軟體崩潰等於安全失效 |
| **用途** | 最後一道實體安全防線 | 常規導航時的障礙回避 |

簡單說：

- **Hardware Collision** = 最後的實體防線，硬體優先於軟體。當軟體全部崩掉時，仍能靠 IO 硬體訊號停止機器人。
- **Software Collision** = 導航時的智慧感知，多層減速/停車，靠感測器資料計算虛擬圍欄。

兩者分開是**安全冗餘**的設計哲學——不把所有安全雞蛋放同一個籃子。

## 只用 Hardware Collision（不用 Software）

| 情境 | 原因 |
|---|---|
| **極低成本機器人** | 沒有 LiDAR/Camera，只有實體安全帶 |
| **極高安全要求** | 任何軟體延遲都不可接受（化工、鋼鐵廠）|
| **純室內固定軌道** | AGV 走在軌道溝槽裡，不需要軟體障礙偵測 |
| **軟體團隊人力不足** | 維護 nav2_collision_monitor 太複雜 |
| **極短反應時間需求** | 微秒級硬體中斷，軟體來不及 |

**典型：傳統工廠 AGV，只有前後紅外線偵測**

---

## 只用 Software Collision（不用 Hardware）

| 情境 | 原因 |
|---|---|
| **研究/實驗室環境** | 需要彈性調整偵測範圍、減速曲線 |
| **精密定位模式** | 需要 `PolygonWarning1/2` 多層減速，讓定位更精準 |
| **模擬環境** | Isaac Sim/Gazebo 沒有真實 IO，硬體collision 無意義 |
| **開發階段除錯** | 軟體監控可以看到視覺化多邊形，方便調整參數 |
| **人形/複雜地形機器人** | 需要動態 footprint + approach 模式，硬體 IO 無法表達 |
| **有其他實體保護** | 人工在旁邊盯著、或圍欄已經物理隔離 |

**典型：研究室的自走車，昂貴的光學雷達掩蓋了腳踏墊的成本**

---

## 兩個都用的正當理由

| 情境 | 解釋 |
|---|---|
| **量產工業 AMR** | 軟體負責導航安全，硬體是最後防線 |
| **人機共存環境** | 軟體多層減速讓人類有預警時間，硬體在軟體失效時托底 |
| **ISO 10218 協作機器人標準** | 法規要求兩種保護機制 |

---

## 結論

**硬體是物理世界最後的信任邊界，軟體是智慧世界的工作馬。**

選用哪個，取決於「你的危險情境是物理式的還是幾何式的」：
- 物理式（撞到就受傷）→ 硬體優先
- 幾何式（撞到障礙物）→ 軟體即可

## 應該做成 BT Node 的情況

| 標準 | 說明 | 例子 |
|---|---|---|
| **有成功/失敗狀態** | 這個動作可能會 fail，需要樹上層節點知道並做決策 | `OpenSoftwareCollisionMonitorService` 會 FAIL |
| **需要被條件節點控制** | 要能被 `Fallback`、`Sequence`、`Loop` 包住 | 碰撞發生後要中斷導航 |
| **需要超時/重試機制** | 這個動作可能會卡住，需要 timeout recovery | 開碰撞監控失敗要重試 |
| **會阻斷或改變流程** | 這個動作失敗時，整個任務應該停止或繞路 | 碰撞了就不前進 |
| **需要 Berth 黑盒封裝** | 這個行為可能被多個地方引用，不想重複寫 | 各個專案都 call 同一個 collision node |
| **需要狀態追蹤** | 這個 action 執行過幾次？成功/失敗？ | `increment_recovery_count()` |

---

## 不需要做成 BT Node 的情況

| 標準 | 說明 | 例子 |
|---|---|---|
| **一次性函式呼叫** | 做完就結束，沒有持續狀態 | 發一個 `/cmd_vel` 就結束 |
| **同步阻塞即可** | 不需要中斷、不需要條件判斷 | `ros2 service call /reset` |
| **沒有失敗情境** | 不可能失敗，或失敗了也不重要 | 純計算函式 |
| **極度頻繁** | 每秒呼叫數百次，做成 node 開銷太大 | 讀取 encoder 位置 |

## 實例對照

```
BT Node ✅：OpenCollisionMonitorService
- 會失敗 → FAILURE → 上層樹可以 Recovery
- 需要等待回應 → on_completion 模式
- 需要 count 追蹤 → recovery_count

一般函式呼叫 ✅：get_current_pose
- 每次回傳當前位置，不會「失敗」
- 高頻率讀取，不需要包成 node 開銷
```

## 總結判斷流程

```
這個功能需要知道「成功了還是失敗了」嗎？
    是 ↓
這個失敗需要被上層邏輯處理嗎？
    是 ↓
這個動作需要超時/重試/中斷嗎？
    是 → 做成 BT Node
    否 → 做成一般 Service/Action Client

    否 ↓
極度高頻或一次性 → 直接函式 / 一般 ROS call
```
