### 3. 架構發現一：Plugin 系統是「stdin/stdout 子進程 + Manifest」

#### 三層 PluginKind

```rust
pub enum PluginKind { Builtin, Bundled, External }
```

每種有不同的 marketplace namespace：
- `builtin` — Rust 程式碼直接建進 binary（`builtin_plugins()` 函式回傳 `example-builtin`）
- `bundled` — 隨 binary 出貨的外掛，讀 `bundled_root()` (在 `crates/plugins/bundled/`，有兩個 fixture: `sample-hooks/`, `example-bundled/`)
- `external` — 從 git URL 或 local path 安裝到 `install_root()`，寫進 `installed.json` registry

#### Plugin Manifest 結構 (`plugin.json` / `.claude-plugin/plugin.json`)

```rust
pub struct PluginManifest {
    name, version, description,
    permissions: Vec<PluginPermission>,    // read | write | execute
    default_enabled: bool,
    hooks: PluginHooks,                    // PreToolUse, PostToolUse
    lifecycle: PluginLifecycle,            // Init, Shutdown
    tools: Vec<PluginToolManifest>,        // 每個 = 一個 CLI 程式
    commands: Vec<PluginCommandManifest>,  // slash command 對應
}
```

#### PluginTool 執行模型 — **stdin/stdout child process**

`PluginTool::execute()` (line 297) 是關鍵：
1. 啟動 `Command::new(&self.command)` 子進程
2. **把 JSON input 從 stdin 寫進去**
3. **讀 stdout 當 result**
4. stderr 失敗時 → `PluginError::CommandFailed`
5. 注入 env vars: `CLAWD_PLUGIN_ID`, `CLAWD_PLUGIN_NAME`, `CLAWD_TOOL_NAME`, `CLAWD_TOOL_INPUT`, `CLAWD_PLUGIN_ROOT`

這就是 Claude Code 的 plugin 模型 — 外掛就是 CLI，不是 in-process Rust library。

#### Plugin 載入流程 (lines 957-1010)

```rust
pub fn discover_plugins(&self) -> Result<Vec<PluginDefinition>, PluginError> {
    self.sync_bundled_plugins()?;                 // 把 bundled 樣板同步到 config_home
    let mut plugins = builtin_plugins();          // 1. 內建
    plugins.extend(self.discover_installed_plugins()?);   // 2. 已安裝 (從 installed.json)
    plugins.extend(self.discover_external_directory_plugins(&plugins)?); // 3. external_dirs/
    Ok(plugins)
}
```

#### Registry 衝突偵測 (`PluginRegistry::aggregated_tools`, line 695)

```rust
for tool in plugin.tools() {
    if let Some(existing_plugin) =
        seen_names.insert(tool.definition().name.clone(), tool.plugin_id().to_string())
    {
        return Err(PluginError::InvalidManifest(format!(
            "plugin tool `{}` is defined by both `{existing_plugin}` and `{}`",
            ...
        )));
    }
}
```

兩個 plugin 定義同名 tool → 啟動時就 fail-fast。比 runtime 衝突好處理。

#### 安裝 / 升級 API (lines 980-1010)

- `install(source)` — source 可以是 local path 或 git URL (`parse_install_source`)
- materializes 到 `install_root/.tmp/`，驗證 manifest，搬進正式位置，寫進 registry
- 既有 path → `fs::remove_dir_all` 清掉再裝（沒做備份）
- `update` 流程類似
- 啟用狀態寫到 `settings.json` 的 `enabledPlugins` map

#### 對未來在我們系統使用的影響

- **好處**：plugin 系統已經是「process boundary」設計，每個外掛都是獨立行程，不會 crash 主進程、不會 leak Rust 物件
- **代價**：每次 tool call 都要 fork+exec，沒有 persistent worker pool；大量外掛時會有 fork 開銷
- **環境變數命名**：`CLAWD_*` (clawd 不是 claw)，注意 shell 變數拼字
- 如果要借鏡，**PluginTool 改成 WebSocket / Named Pipe** 比 stdin/stdout 更適合多輪對話 plugin

### 4. 架構發現二：compat-harness 是「**parse upstream TS source 拿 manifest**」

這是整個 repo 最聰明、也最容易壞掉的設計。

#### 行為

`compat_harness::extract_manifest(paths)`：
1. 讀三個檔案：`src/commands.ts`, `src/tools.ts`, `src/entrypoints/cli.tsx` (來自「upstream TypeScript repo」)
2. 用**正則/字串掃描** (不是 AST parser) 抽出：
   - **commands**：`extract_commands` 找 `import ... from "./commands/..."` 拿 builtin，找 `feature('...')` 拿 feature-gated，排除 `INTERNAL_ONLY_COMMANDS` block
   - **tools**：`extract_tools` 找 import 拿 `*Tool` symbol，找 `feature('...')` 拿 conditional tool
   - **bootstrap plan**：`extract_bootstrap_plan` 用 `String::contains` 偵測 upstream 有哪些 fast-path（`--version` → `FastPathVersion`, `startupProfiler` → `StartupProfiler`, `daemon` → `DaemonFastPath` …），最後一定加 `MainRuntime`
3. 回傳 `ExtractedManifest { commands, tools, bootstrap }`

#### 為什麼這樣設計

`PARITY.md` 開頭明說：
> Method: compared feature surfaces, registries, entrypoints, and runtime plumbing only. **No TypeScript source was copied.**

不複製 TS 程式碼，但**指令清單、tool 清單、bootstrap 順序** 必須跟 upstream 鎖齊。
最便宜的做法：直接 parse 上游 TS source，把 import 行當 manifest。

#### 路徑解析策略 (`UpstreamPaths::from_workspace_dir`)

依序找 upstream repo：
1. `CARGO_MANIFEST_DIR/../..` 自身 (primary)
2. 環境變數 `CLAUDE_CODE_UPSTREAM`
3. 往上 4 層 ancestor 的 `../claw-code` 或 `../clawd-code` sibling
4. `reference-source/claw-code/`
5. `vendor/claw-code/`

**找到的條件是 `src/commands.ts` 存在**。

#### 目前 worktree 狀態 — **compat-harness 死碼**

`ls src/commands.ts` → 檔案不存在
`ls src/tools.ts` → 檔案不存在
`ls src/entrypoints/cli.tsx` → 檔案不存在 (只有 `src/entrypoints/__init__.py`)

也就是說：
- 我們這個 worktree 的 `src/` 是 **Python port** (昨天報告的 shim layer)
- 上游 **TypeScript** 源碼根本沒拉進來
- `dump-manifests` / `bootstrap-plan` 子命令在目前 layout 下會 fail 或回空
- 測試裡 `has_upstream_fixture()` 檢查不通過就 return（skip），所以 CI 在沒有 fixture 時會 silently pass

#### 對未來在我們系統使用的影響

這是個 **重要架構訊號**：

| 選項 | 優點 | 缺點 |
|---|---|---|
| A. 維持 TS-source 解析 | 與 upstream 鎖齊零成本 | 脆，upstream 改 import 風格就壞 |
| B. 改用自己寫的 manifest 檔 (YAML/TOML) | 強健、版本可控 | 雙重維護負擔 |
| C. 從 PyPI / npm package metadata 拿 | 動態、語意化 | 對 fork 過的 fork 不適用 |
| D. 用 syn / tree-sitter-typescript 做真的 AST parse | 抗重構 | 編譯時間 + 二進制大小 |

**對我們的建議**：
- 如果只是要看「Claude Code 的指令/工具有哪些」，A 已經夠
- 如果要長期 fork 並發布，**改成 B + 從 upstream dump 出 seed manifest** 比較好
- 無論如何，**compat-harness 在當前 worktree 是 dead code**，需要先把 `src/commands.ts` 拉進來 (從 `ultraworkers/claw-code` 的 main branch 或 `anthropics/claude-code` 的某 snapshot) 才會活

### 5. 比較圖：Rust core 的依賴結構

```
rusty-claude-cli (binary, 4846 行 main.rs)
   │
   ├── api         (Anthropic HTTP, SSE, types)
   ├── commands    (slash command dispatch, 1545 行)
   ├── tools       (GlobalToolRegistry = builtin ∪ plugin)
   │      └── plugins  ← 注入 plugin tools
   ├── compat-harness  (parse upstream TS, 357 行)
   ├── runtime     (核心)
   │      ├── conversation  (turn loop)
   │      ├── session       (JSONL persistence)
   │      ├── config        (settings.json, .mcp.json)
   │      ├── permissions   (mode + rules)
   │      ├── mcp_stdio     (MCP stdio transport, 1697 行)
   │      ├── hooks         (PreToolUse / PostToolUse)
   │      ├── prompt        (system prompt builder)
   │      ├── bootstrap     (phase enum)
   │      ├── compact       (auto-compaction)
   │      ├── oauth         (PKCE, callback server)
   │      ├── remote        (upstream proxy support)
   │      ├── usage         (token / USD)
   │      └── file_ops      (read/write/edit/grep/glob)
   ├── plugins     (PluginManager, 2935 行)
   └── crossterm + rustyline + pulldown-cmark + syntect  (TUI)
```

**Plugins 是 `runtime` 之下的依賴**，但 `tools` 同時吃 `runtime` 和 `plugins`。
所以 plugin tools 在 agent loop 裡的呼叫路徑是：

```
ConversationRuntime → ToolExecutor trait
                        ↓
                  (main.rs 接的 closure)
                        ↓
                  GlobalToolRegistry::execute(name, input)
                        ↓
                  matches handler: Builtin | Plugin(tool)
                        ↓ Plugin
                  PluginTool::execute → Command::spawn()
```

**`PluginTool` 從來沒被 `ConversationRuntime` 直接知道** — main.rs 在 closure 裡把 registry 注入進去。
這是個乾淨的 dependency-inversion。
